# SD Spec - 规格文档管理

## 目的
管理规范驱动开发(SD)的 `spec.md` 文档。确保需求规格文件的一致创建、更新和检索，同时**严格分离"构建什么"(Spec)与"如何构建"(Design)**。

## 前置条件
项目目录结构：
```
.sd/
└── specs/
    └── {{feature-name}}/
        └── spec.md
```
`.sd/specs/{{feature-name}}/` 目录必须存在（由 sd-init 创建）。

## 触发条件
- 用户请求创建/编写/更新规格文档
- 用户说"写规格"、"创建规格"、"write spec"、"create spec"
- sd-init 成功完成后
- 用户想查看或修改已有的 spec.md

## 核心能力

### 1. 创建规格文件
按以下步骤生成新的 `spec.md` 文件：

1. **验证目录：** 检查 `.sd/specs/{{feature-name}}/` 是否存在
2. **检查存在性：** 检查该目录下是否已有 `spec.md`
3. **生成内容：** 若不存在，结合用户需求与 `spec_template.md` 的结构/要求生成 spec.md
4. **严格格式：** spec.md 格式必须严格遵循 `spec_template.md` 结构
5. **填充章节：** 包含模板中的所有必需章节，按用户需求填充内容
6. **EARS合规：** 所有验收条件必须遵循EARS格式模式
7. **禁止覆盖：** 若 spec.md 已存在，告知用户并建议使用更新操作

### 2. 更新规格文件
更新已有 `spec.md` 文件的规则：

1. **目标文件：** 所有修改仅写入 `.sd/specs/{{feature-name}}/spec.md`
2. **保持结构：** 更新时维持模板章节结构
3. **全文重写：** 用户提供编辑内容时，清空并重写整个 spec.md
4. **增量更新：** 用户请求特定章节更新时，仅修改该章节，保留其他章节
5. **更新后验证：** 确保更新后的内容仍符合"构建什么"约束

### 3. 读取与搜索规格文件
- **特性规格：** `.sd/specs/{{feature-name}}/spec.md`
- 使用 `Grep` 搜索特定需求、场景或关键词
- 使用 `Read` 加载完整规格内容以供审查或修改
- 以结构化格式返回搜索/读取结果（章节标题 + 匹配内容片段）
- 通过 `Glob` 支持列出所有特性规格文件

## 关键约束：规格 vs 设计

### 规格定义"构建什么"（允许的内容）
- 系统的外部业务行为（面向用户的功能）
- 业务规则、验证逻辑和约束
- 用户场景、验收条件、成功/失败条件
- 产品经理、测试人员和业务干系人的视角
- 使用OpenSpec约定的需求（SHALL/MUST关键字、场景块）
- DFX约束（性能、可靠性、安全性、可维护性、兼容性）
- 领域术语和数据逻辑约束
- 角色定义和交互边界

### 严格禁止的内容（设计细节）
不得在 spec.md 文件中包含以下任何内容：
1. 数据库模式（表、列、数据类型、索引）
2. 技术架构（类图、接口继承、函数签名）
3. 基础设施决策（缓存策略、消息队列、中间件）
4. 实现细节（算法、性能优化、代码结构）
5. API端点定义（HTTP方法和路径）
6. 技术栈选择（框架、库）
7. 任何回答"如何构建"而非"构建什么"的内容

## 执行指南
1. 创建/更新前始终验证文件路径（使用 `Glob` 确认目录结构）
2. 在所有规格文件中保持OpenSpec格式（需求标题、场景块、增量标记）
3. 破坏性操作（覆盖、删除）前提示用户确认
4. 默认语言：中文（除非用户另有要求）
5. 所有验收条件必须使用EARS格式模式
6. 每条业务规则必须有可验证的验收条件

## 模板参考
spec_template.md 定义以下必需章节：

1. **组件定位** - 核心职责、输入、输出、边界
2. **领域术语** - 统一语言定义
3. **角色与边界** - 核心角色、外部系统、交互上下文(PlantUML)
4. **DFX约束** - 性能、可靠性、安全性、可维护性、兼容性
5. **核心能力** - 每个模块的业务规则、交互流程、异常场景
6. **数据约束** - 领域对象逻辑约束

详见 `templates/spec_template.md` 和 `templates/ears-format.md`。
