# SD Verify - 代码-设计一致性验证

## 目的
在编码完成后，对照设计文档(design.md)逐一验证代码实现的完整性和一致性，确保"设计即所码，码即所设计"，产出结构化的代码-设计一致性检查报告。

## 前置条件
项目目录结构：
```
.sd/
└── specs/
    └── {{feature-name}}/
        ├── spec.md      ← 需求规格
        ├── design.md    ← 技术设计（必须存在）
        ├── tasks.md     ← 任务清单
        └── verify-report.md  ← 一致性检查报告（本skill产出）
```

**重要：** `.sd/specs/{{feature-name}}/design.md` 必须存在，且代码实现已完成。

## 触发条件
- 用户请求验证代码与设计的一致性
- 用户说"验证代码"、"检查一致性"、"sd verify"、"verify design"
- 编码任务完成后
- sd-tasks 中的所有任务标记为完成后

## 核心工作流

### 第1步：设计文档解析与基准提取

读取 `.sd/specs/{{feature-name}}/design.md`，提取以下基准信息：

1. **模块列表**
   - 设计文档中定义的所有模块及其职责
   - 每个模块的预期文件路径
   
2. **接口列表**
   - 设计文档中定义的所有API接口
   - 接口路径、HTTP方法、请求/响应格式
   
3. **数据模型列表**
   - 设计文档中定义的所有数据表/实体/字段
   - 字段类型、约束条件、索引
   
4. **文件结构预期**
   - 设计文档中描述的目录和文件组织
   - 关键文件的路径
   
5. **关键流程**
   - 设计文档中描述的核心业务流程
   - 流程步骤和决策点

### 第2步：代码库扫描与事实采集

使用工具扫描项目代码库，采集实际实现信息：

1. **目录结构扫描**
   ```
   使用 glob 扫描项目目录结构
   glob: "src/**/*"  → 获取所有源代码文件
   glob: "tests/**/*" → 获取所有测试文件
   ```

2. **关键代码模式搜索**
   ```
   使用 grep 搜索关键模式：
   - 路由/接口定义：grep "router\.(get|post|put|delete)" 或 grep "@RequestMapping"
   - 数据模型定义：grep "class.*Model" 或 grep "type.*struct" 或 grep "@Entity"
   - 模块入口和导出：grep "export" 或 grep "module.exports"
   ```

3. **关键文件阅读**
   ```
   使用 read 逐个阅读关键代码文件，确认实际实现内容
   ```

### 第3步：功能一致性检查

逐项对比设计文档定义的功能与代码实际实现：

| 检查项 | 验证方法 |
|-------|---------|
| 功能模块 | 设计中的每个模块，代码中是否有对应实现 |
| 行为逻辑 | 功能的输入输出是否与设计定义一致 |
| 边界条件 | 异常处理是否与设计方案一致 |
| 流程一致性 | 设计流程图与代码实际执行路径是否匹配 |

**功能一致性判定标准：**

| 状态 | 判定条件 |
|------|---------|
| 完全一致 | 设计中的功能描述与代码实现逻辑完全匹配 |
| 基本一致 | 核心逻辑一致，但存在非关键差异 |
| 部分一致 | 只实现了部分设计要求 |
| 未实现 | 设计中定义的功能在代码中完全找不到 |
| 超出设计 | 代码中存在设计文档未提及的功能（需标注） |

### 第4步：代码与设计对应检查

#### 4.1 模块对应检查

验证设计文档中的每个模块是否在代码中有对应：

| 设计模块 | 代码文件/目录 | 对应状态 | 差异说明 |
|---------|-------------|---------|---------|
| 模块名称 | src/module/ | 已对应/部分对应/未对应 | ... |

**输出要求：明确指出设计文档哪个模块对应代码的哪几行**

示例：
```
设计模块：用户管理模块
设计文档位置：design.md 第2.1节
代码实现位置：src/modules/user/user.service.ts
具体对应：
  - 用户注册功能 → user.service.ts:15-45 (Register方法)
  - 用户登录功能 → user.service.ts:47-78 (Login方法)
  - 用户信息查询 → user.service.ts:80-102 (GetUserInfo方法)
```

#### 4.2 接口对应检查

| 设计接口 | 代码实现位置 | HTTP方法 | 请求格式 | 响应格式 | 状态 |
|---------|------------|---------|---------|---------|------|
| POST /api/users | src/routes/user.ts:12 | POST | 一致/不一致 | 一致/不一致 | 已对应/部分/未对应 |

**输出要求：明确指出设计接口对应代码的哪几行**

示例：
```
设计接口：POST /api/users/register
设计文档位置：design.md 第3.2节
代码实现位置：src/routes/user.ts:25-40
具体对应：
  - 路由定义 → user.ts:25
  - 参数验证 → user.ts:27-32
  - 业务逻辑调用 → user.ts:34
  - 响应构造 → user.ts:36-39
```

#### 4.3 数据模型对应检查

| 设计数据模型 | 代码实现位置 | 字段对应 | 类型一致 | 状态 | 缺失字段 |
|------------|------------|---------|---------|------|---------|
| User | src/models/user.ts | 8/10 | 7/8 | 已对应/部分/未对应 | status, last_login |

**输出要求：明确指出设计数据模型对应代码的哪几行**

示例：
```
设计数据模型：User
设计文档位置：design.md 第4.1节
代码实现位置：src/models/user.entity.ts
具体对应：
  - id字段 → user.entity.ts:5 (number类型)
  - username字段 → user.entity.ts:7 (string类型)
  - email字段 → user.entity.ts:9 (string类型)
  - password字段 → user.entity.ts:11 (string类型，加密存储)
  缺失字段：status (设计要求，代码未实现)
```

### 第5步：代码真实存在性检查

验证设计文档中提及的所有代码要素是否真实存在：

#### 5.1 文件存在性检查
```
使用 glob 验证设计文档中提到的文件路径是否真实存在
```

| 设计提及的文件路径 | 是否存在 | 状态 |
|------------------|---------|------|
| src/config/database.ts | 是/否 | 已存在/缺失 |

#### 5.2 函数/方法存在性检查
```
使用 grep 搜索设计文档中定义的类名、方法名
```

| 设计提及的函数 | 代码中搜索结果 | 状态 |
|--------------|-------------|------|
| UserService.create() | src/services/user.ts:25 | 已存在/缺失 |

#### 5.3 空实现/占位代码检查
```
使用 read 阅读代码文件，检查是否存在空实现
```

检查以下空实现类型：
- 只有 `pass`、`TODO`、`FIXME` 注释
- 抛出 `NotImplementedError`
- 返回硬编码数据，没有实际业务逻辑
- 函数体为空或只有注释

| 文件 | 函数/方法 | 空实现类型 | 状态 |
|------|----------|-----------|------|
| src/services/user.ts | delete() | 只有 TODO 注释 | 空实现 |

### 第6步：生成一致性检查报告

将检查结果写入 `.sd/specs/{{feature-name}}/verify-report.md`：

### 2. 总体一致性评分

| 检查维度 | 一致率 | 评级 |
|---------|-------|------|
| 功能一致性 | X/Y (Z%) | 一致/基本一致/不一致 |
| 模块对应性 | X/Y (Z%) | 一致/基本一致/不一致 |
| 接口对应性 | X/Y (Z%) | 一致/基本一致/不一致 |

| **综合评级** | | **通过/有条件通过/不通过** |

**评级标准：**
- 一致率 >= 90%：一致
- 一致率 70%-89%：基本一致
- 一致率 < 70%：不一致
- 综合评级：所有维度均为"一致"则"通过"，任一维度为"不一致"则"不通过"，其余为"有条件通过"

## 检查工具使用指南

### 使用 glob 验证文件存在

```
glob: "src/**/*.ts"    → 获取所有 TypeScript 文件列表
glob: "src/**/user*"   → 搜索与 user 相关的文件
glob: ".sd/specs/*/design.md" → 获取所有设计文档
```

### 使用 grep 验证函数/类存在

```
grep: "class UserService"   → 搜索 UserService 类定义
grep: "def create"          → 搜索 create 方法定义
grep: "async register"      → 搜索 register 异步函数
grep: "router\.(get|post)"  → 搜索路由定义
```

### 使用 read 验证具体实现

```
read: "src/services/user.ts"    → 阅读 User 服务实现
read: ".sd/specs/feature/design.md" → 读取设计文档
```

## 执行指南

1. 验证前必须确认 design.md 存在
2. 扫描代码库时，记录所有实际存在的文件
3. 对于缺失的代码，明确指出设计文档中的位置
4. 对于不一致的实现，详细说明差异点
5. 生成报告时，必须包含行号映射（设计位置→代码行号）
6. 默认语言：中文

## 与其他SD Skill的衔接

### 输入
- **design.md**：提供设计基准
- **spec.md**：提供需求背景（可选）
- **tasks.md**：提供任务清单（用于判断任务完成状态）

### 输出
- **verify-report.md**：一致性检查报告
- 问题清单（阻断性问题、一般问题、建议改进）

### 触发时机
- 在编码任务完成后
- 在 sd-tasks 中所有任务标记完成后

## 下一步

验证完成后：
- 若通过：可以进入部署阶段
- 若有条件通过：建议修复一般问题后再部署
- 若不通过：必须修复阻断性问题后重新验证
