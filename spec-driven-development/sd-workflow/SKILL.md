# SD Workflow - 规范驱动开发全流程协调

## 目的
协调规范驱动开发(SD)的完整工作流程，按照正确的顺序驱动各个skill执行，确保文档间的一致性和完整性。提供从需求到实现任务的端到端引导。

## 触发条件
- 用户说"开始SD开发"、"sd workflow"、"sd start"、"规范驱动开发"
- 用户提供了完整的需求描述并希望走完整SD流程
- 用户想查看当前SD流程的进度状态

## 核心工作流

### 完整流程（5个阶段）

```
用户需求描述
     ↓
[阶段1] sd-init → 创建 .sd/specs/{feature-name}/ 目录
     ↓
[阶段2] sd-spec → 创建 spec.md（"构建什么"）
     ↓
[阶段3] sd-design → 创建 design.md（"如何构建"）
     ↓
[阶段4] sd-tasks → 创建 tasks.md（"实现步骤"）
     ↓
[阶段5] 编码实现 → 按 tasks.md 完成代码开发
     ↓
[阶段6] sd-verify → 验证代码与设计一致性
     ↓
验证通过，可部署
```

### 阶段1：初始化 (sd-init)
1. 调用 sd-init skill
2. 从用户需求生成 feature_name
3. 创建目录结构 `.sd/specs/{feature_name}/`
4. **检查点：** 目录创建成功

### 阶段2：规格编写 (sd-spec)
1. 调用 sd-spec skill
2. 基于用户需求和 spec_template.md 生成 spec.md
3. **用户审阅：** 展示生成的 spec.md，请用户确认或修改
4. **检查点：** spec.md 存在且内容完整

### 阶段3：设计编写 (sd-design)
1. 调用 sd-design skill
2. 读取 spec.md 作为需求上下文
3. 基于 design_template.md 生成 design.md
4. **用户审阅：** 展示生成的 design.md，请用户确认或修改
5. **一致性检查：** 确认 design.md 覆盖 spec.md 中所有需求

### 阶段4：任务生成 (sd-tasks)
1. 调用 sd-tasks skill
2. 读取 spec.md 和 design.md
3. 生成 tasks.md 实现任务清单
4. **用户审阅：** 展示生成的 tasks.md，请用户确认任务顺序和粒度
5. **检查点：** tasks.md 存在且所有需求/设计都有对应任务

### 阶段5：编码实现
1. 用户按 tasks.md 中的任务顺序逐个实现代码
2. 每完成一个任务，更新 tasks.md 中的状态
3. 所有任务完成后，进入验证阶段

### 阶段6：一致性验证 (sd-verify)
1. 调用 sd-verify skill
2. 读取 design.md 作为验证基准
3. 扫描代码库，采集实际实现信息
4. 逐项验证功能一致性、模块对应、接口对应、数据模型对应
5. 检查代码真实存在性（文件、函数、无空实现）
6. 生成 verify-report.md 一致性检查报告
7. **检查点：** 验证报告生成，问题清单明确

## 流程状态检查

### 查看当前进度
扫描 `.sd/specs/{feature-name}/` 目录，检查文件存在情况：

| spec.md | design.md | tasks.md | verify-report.md | 状态 |
|---------|-----------|----------|-----------------|------|
| ✗ | ✗ | ✗ | ✗ | 未初始化 → 执行 sd-init |
| ✓ | ✗ | ✗ | ✗ | 规格完成 → 执行 sd-design |
| ✓ | ✓ | ✗ | ✗ | 设计完成 → 执行 sd-tasks |
| ✓ | ✓ | ✓ | ✗ | 任务完成 → 开始编码实现 |
| ✓ | ✓ | ✓ | ✓ | 验证完成 → 可部署或修复问题 |
| ✗ | ✓ | ✗ | ✗ | 异常 → 缺少规格，先执行 sd-spec |
| ✗ | ✗ | ✓ | ✗ | 异常 → 缺少规格和设计，建议重新开始 |

### 从中断点恢复
- 检测已有文件，从最后完成的阶段继续
- 不重新创建已存在的文档（除非用户明确要求）

## 一致性保障

### 规格-设计对齐
- spec.md 中每个核心能力模块必须在 design.md 中有对应实现模型
- spec.md 中每个 DFX 约束必须在 design.md 中有技术方案
- 未覆盖的需求应生成警告清单

### 设计-任务对齐
- design.md 中每个组件/接口必须在 tasks.md 中有对应任务
- tasks.md 中不应存在无设计依据的任务
- 未覆盖的设计组件应生成警告清单

### 规格-任务对齐
- spec.md 中每个业务规则必须在 tasks.md 中有验证任务
- 验收条件必须有对应的测试任务

### 代码-设计一致性（新增）
- design.md 中每个模块必须在代码中有对应实现文件
- design.md 中每个接口必须在代码中有对应路由定义
- design.md 中每个数据模型必须在代码中有对应实体类
- 所有代码实现必须有明确的行号映射到设计文档
- 代码中不应存在空实现或占位代码

## 执行指南
1. 每个阶段完成后等待用户确认再进入下一阶段
2. 支持用户在任意阶段暂停，稍后从断点恢复
3. 支持用户单独跳转到某个阶段（前提是前置条件满足）
4. 一致性检查不通过时生成警告，但不阻止流程继续
5. 默认语言：中文
6. 完整流程结束后输出项目文件结构总览

## 完成后输出
```

.sd/
└── specs/

        ├── spec.md           ← 需求规格（构建什么）

        └── verify-report.md  ← 一致性检查报告（代码-设计验证结果）

- 通过：可以进入部署阶段
- 有条件通过：建议修复一般问题后再部署
- 不通过：必须修复阻断性问题后重新验证
```
